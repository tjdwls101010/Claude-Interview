# Harness Spec — `/interview` 스킬 하네스

## Context

이 저장소(`/Users/seongjin/Coding/Interview`)의 유일한 산출물은 명시 호출 전용 인터뷰 스킬이다. 프로젝트 범위 Claude Code 하네스는 `.claude/skills/interview/SKILL.md` 하나와 이 명세로 구성되며, `CLAUDE.md`도 `.claude/settings.json`도 없다. 스킬 디렉터리는 `~/.claude/skills/interview`로 심링크되어 있어 이 저장소가 원본이고 모든 프로젝트에서 사용자 스코프로 쓰인다 — 즉 이 저장소의 편집은 즉시 전역에 적용된다.

이 명세는 2026-08-16에 복구했으나, 그 복구는 다른 저장소(Ouroboros)의 명세를 출발점으로 삼았고 그 과정에서 이 저장소에 존재한 적 없는 B1~B3이 함께 들어왔다. 2026-08-22에 `retired`로 정리했다(아래 Change history 참조).

사용자는 하네스 설계 용어에 익숙하고 한국어로 협업한다. 새 스킬 본문은 다른 프로젝트에도 옮겨 쓸 수 있도록 영문으로 쓰되, 실행 중 질문과 최종 계획 문서는 사용자의 대화 언어를 따른다.

## Goals

- 사용자가 `/interview`를 명시적으로 호출했을 때만 시작하며, 제품 고유 인터뷰·실행 시스템을 전혀 모르는 상태에서도 모든 종류의 프로젝트에 사용할 수 있는 자체 완결형 인터뷰를 제공한다.
- 조사 가능한 사실과 사용자의 가치 결정을 분리하고, 근거·반례·반대 가정을 사용해 구현 방향을 바꿀 불확실성을 승인 전에 해소한다.
- 눈앞의 질문 횟수가 아니라 계획, 구현, 잘못 구현된 결과의 수정까지 포함한 사용자 총부담을 최소화한다. 조사로 없앨 수 있거나 답이 계획을 바꾸지 않는 질문은 생략하되, 어림짐작의 재작업 비용이 답변 비용보다 큰 방향 변경 질문은 귀찮아 보인다는 이유로 생략하지 않는다.
- 목표, 성공 기준, 범위, 제약, 인터페이스, 순서, 단계별 완료 판정, 검증, 위험까지 결정된 계획에 사용자가 명시적으로 합의하게 한다.
- 승인된 계획 문서만 저장하고 끝낸다. 인터뷰 중간 상태, 구현, Git 작업, 외부 실행 파이프라인은 만들거나 호출하지 않는다.

## Component specs

### `.claude/skills/interview/` (B4~B14, B26~B30)

- **명령 인터페이스** — 프로젝트 스킬 디렉터리 이름에서 `/interview`가 만들어진다. 인자를 받지 않으며, 호출 직후 다른 조사보다 먼저 `AskUserQuestion`으로 주제·목적·기대 결과를 한 번에 자유서술로 받는다. 이 "먼저"에는 서브에이전트 실행이 명시적으로 포함된다(B30).
- **프론트매터** — `name`, `description`, `disable-model-invocation: true`만 사용한다. `description`은 수동 호출 전용, 계획 저장 전용, 구현·Git 금지를 명시한다. `allowed-tools`는 사용하지 않는다.
- **언어** — 본문은 영문이다. 질문, 요약, 승인안, 저장하는 계획은 사용자가 대화에 쓰는 언어를 따른다.
- **본문 구조** — Mission and boundaries → Evidence and authority model → Objective-aligned candor → Context-first interview loop → Question interface → Breadth and revision handling → Risk-based independent review → Completion and approval → Plan artifact contract → Persistence, interruption, and prohibited follow-on work 순서를 고정한다.
- **증거 계약** — 로컬 자료를 먼저 읽고, 계획이 바뀔 수 있는 최신·고위험 외부 사실만 권위 있는 출처로 검증한다. 사실, 출처 있는 추론, 사용자 결정, 명시적 가정, 미해결을 구분하며 외부 관찰을 요구사항으로 자동 승격하지 않는다.
- **인터뷰 계약** — 결정 지도를 유지하고 가장 파급력이 큰 불확실성을 조사와 비판적 질문으로 줄인다. 질문 수나 순서를 고정하지 않고, 조사로 답할 수 있는 사실 대신 사용자만 정할 수 있는 가치·우선순위·권한을 묻는다. 루프의 스윕 단계는 전체 트랙 명부를 대화 텍스트로 출력해야 충족되고(B27), 영향 스윕은 영향 없다고 판정한 항목까지 이름을 댄다(B29).
- **발산 계약** — 명부 제시는 상태 보고가 아니라 인터뷰어의 프레임을 물려받지 않은 사용자에게 빠진 트랙을 요청하는 행위다. 발산 국면에서는 미리 만든 선택지가 답을 인터뷰어가 이미 생각한 것으로 좁히므로 명부와 초대를 산문으로 쓰고, `AskUserQuestion`은 명부의 완결성 자체가 방향을 바꾸는 결정이 된 뒤에만 쓴다(B28). 이 초대는 모든 사용자 질문을 `AskUserQuestion`으로 하라는 규칙의 유일한 예외이므로, 그 규칙 자체에 예외와 이유를 함께 적어 둔다 — 적지 않으면 두 조항이 정면으로 충돌한다.
- **질문 비용 계약** — 눈에 보이는 질문 수가 아니라 계획부터 재작업까지 사용자가 치르는 총비용을 최적화한다. 첫 자유서술 브리프 이후의 질문은 조사로 불확실성을 줄이고 답이 바꿀 결정을 명시하며 근거 있는 추천을 제공한다. 답이 방향을 바꿀 수 있고 잘못 추측한 구현의 수정 비용이 더 크다면, 추가 질문이 귀찮아 보인다는 이유만으로 생략하지 않는다.
- **검토 계약** — 독립 검토의 이득이 실제로 있는 위험 표면만 중복 제거한 lane으로 제안한다. `AskUserQuestion`으로 비용과 범위를 승인받은 경우에만 위험별 서브에이전트를 병렬 실행하고, 메인 인터뷰어가 출처와 모순을 재검증한 뒤 사용자 결정만 다시 묻는다. lane은 런타임이 티어 선택을 허용할 때 인터뷰어 종합보다 가벼운 티어를 기본으로 하며, 종합 전용 상위 티어 에이전트는 두지 않는다(B11).
- **종료 계약** — 방향을 바꾸는 미해결 결정이나 모순이 없을 때 한 문장 목표와 전체 계획을 보여 주고 `AskUserQuestion`으로 승인받는다. 승인 전에는 쓰지 않고, 승인 후에는 합의된 Markdown 계획만 저장하고 재독해한다.
- **산출물 계약** — 계획은 목표/요약, 확인된 현재 상태와 근거, 성공 기준, 범위·비범위·제약, 핵심 결정과 이유, 관련 도메인의 인터페이스·산출물·데이터 흐름, 순서·의존성·단계별 완료 판정, 검증 시나리오, 위험·가정·비차단 보류를 포함한다. 해당 없는 도메인 항목은 만들지 않는다.
- **번들 파일** — 모든 실행 경로가 같은 인식론·종료·저장 계약을 필요로 하므로 `SKILL.md` 한 파일로 유지하며 reference, script, custom agent, workflow, hook을 추가하지 않는다.

## Design rationale

**왜 제품의 기존 인터뷰 흐름과 분리하는가.** 이번 목표는 특정 제품의 세션, 점수, 실행 단계 없이도 어떤 프로젝트에서든 계획 합의까지 갈 수 있는 독립 명령이다. 기존 배포용 스킬이나 제품 코드를 재사용하면 외부 상태와 용어가 인터뷰의 숨은 전제가 되므로, 프로젝트 범위 `/interview`는 대화와 일반 도구만으로 자체 완결한다.

**왜 수동 호출만 허용하는가.** 인터뷰는 여러 차례 사용자의 결정과 마지막 계획 파일 쓰기를 수반하므로 사용자가 시작 시점을 통제해야 한다. [Claude Code 공식 Skills 문서](https://code.claude.com/docs/en/slash-commands)에 따라 `disable-model-invocation: true`를 사용하면 설명이 자동 호출 컨텍스트에서도 빠지고 사용자 `/interview`만 진입점으로 남는다.

**왜 `allowed-tools`를 두지 않는가.** 이 필드는 도구 풀을 제한하지 않고 호출 턴 동안 나열한 도구를 사전 승인한다. 조사와 저장에 필요한 도구는 프로젝트마다 달라 고정 승인이 맞지 않으며, 기존 권한 경계를 그대로 두는 편이 안전하다.

**왜 증거와 권한을 분리하는가.** 저장소와 외부 출처는 현재 상태와 가능한 결과를 알려 줄 수 있지만 사용자의 우선순위나 수용 가능한 비용을 결정할 권한은 없다. 반대로 사용자는 가치를 결정하지만 검증 가능한 사실을 사실로 바꾸지는 못한다. 두 축을 한 목록에 섞지 않아야 사실 충돌과 가치 선택을 각각 올바른 방식으로 처리할 수 있다.

**왜 질문 수와 모호성 점수를 고정하지 않는가.** 프로젝트마다 독립 결정의 수와 위험 분포가 다르다. 근거 없는 수치는 진척처럼 보이는 거짓 정밀성을 만들고, 고정 wave는 이미 답한 것을 되묻거나 중요한 의존성을 늦게 발견하게 만든다. 대신 결정 완결성의 관찰 가능한 조건을 종료 기준으로 쓴다.

**왜 질문 횟수가 아니라 사용자 총부담을 최적화하는가.** 계획 단계의 짧은 답변 한 번과 잘못 구현된 결과를 발견한 뒤 계획을 고치고 코드를 되돌리거나 다시 만드는 비용은 대칭이 아니다. 모델이 당장의 대화 마찰만 줄이면 가장 비싼 불확실성을 추측으로 덮을 수 있다. 반대로 이 비대칭은 많은 질문 자체를 정당화하지 않으므로, 조사로 없앨 수 있거나 답이 계획을 바꾸지 않는 질문을 먼저 제거하고 남은 방향 변경 결정만 묻는다.

**왜 검토 lane을 동적으로 구성하는가.** 보안, 법률, 접근성, 마이그레이션처럼 독립 전문 판단이 필요한 위험은 병렬 검토의 이득이 크지만, 모든 계획에 고정 패널을 실행하면 비용과 중복만 늘어난다. 실패 표면으로 중복 제거하고 사용자 승인 후에만 실행하면 독립성의 이득과 비용을 함께 통제할 수 있다.

**왜 스윕을 훈계가 아니라 눈에 보이는 산출물로 바꾸는가.** 실사용에서 인터뷰가 한 트랙만 파고드는 증상이 나왔다. 루프 1단계는 파급력이 가장 큰 미해결 항목 하나를 고르고 3단계는 가장 작은 probe를 고르므로 1→3은 정의상 탐욕적 하강이고, 유일한 반작용이던 6단계 스윕은 순수한 훈계였다. 문제의 핵심은 직렬 스레드가 자기 커버리지를 감사하는데 그 감사에 쓰는 프레임이 애초에 빈틈을 만든 그 프레임이라는 데 있다 — 자기가 생각 못 한 것을 자기 프레임으로 찾을 수는 없다. 스킬이 "universal categories를 강요하지 말라"고 이미 써 놨는데도 터널비전이 난 이유가 이것이다. 그래서 처방은 더 강한 훈계가 아니라 명부를 대화 밖으로 내보내는 것이다.

**왜 발산원이 사용자인가, 그리고 왜 그 초대는 메뉴가 아닌가.** 프레임이 다른 관찰자가 필요한데 이 인터뷰에는 이미 한 명 있다. 사용자는 도메인 지식을 갖고 있으면서 메인 스레드의 프레임을 물려받지 않은 유일한 관점이고 토큰 비용이 0이다. 이전 설계가 그 관점을 못 쓴 이유는 스윕이 대화에 나타나지 않아 반박할 물건이 없었기 때문이다. 다만 이 초대를 `AskUserQuestion`으로 하면 처방이 스스로를 무너뜨린다 — 미리 만든 선택지는 답을 인터뷰어가 이미 생각한 것들로 좁히는데 그게 정확히 발산의 반대다. 스킬은 이 논리를 오프닝 질문에 대해 이미 알고 있었고, 이번 변경은 같은 논리를 명부까지 확장한다.

**왜 B24·B25를 재검토하고 다시 기각했는가.** 최초 가설은 발산을 dynamic workflow fan-out으로 얻는 것이었고 6개 렌즈와 3개 적대 검증을 거쳐 기각됐다. 근거는 넷이다. 첫째, 스킬의 유일한 하드 불변식인 "승인 전 모든 활동은 읽기 전용"이 지금 참인 이유는 평범한 Task 서브에이전트가 세션의 권한 모드를 상속하기 때문인데, 워크플로 에이전트는 상속하지 않고 무조건 `acceptEdits`로 돌며 세션 도구 allowlist를 물려받는다. 검토 lane은 승인 전에 뜨므로 프롬프트도 체크인도 없이 쓰기 권한이 열린다. 둘째, 런타임 비용 고지는 그때 `/interview`를 돌리는 사람에게 받는 동의이지 스펙이 근거와 함께 닫아 둔 불변식을 푸는 결재가 아니며, 워크플로 실행 프롬프트는 같은 결정에 대한 두 번째 승인 UI가 된다. 셋째이자 결정적으로, fan-out을 정당화하는 교리("적대적 재검토를 통과한 발견이 더 믿을 만하다")는 이미 제기된 주장의 오탐을 걷어내는 precision 논증인데 관찰된 실패는 애초에 안 열린 가지, 즉 recall 문제다. 적대적 검증은 recall을 올리지 않는다. 넷째, 발견 단계 fan-out은 자기 논리로도 무너진다 — N개의 렌즈를 메인 스레드가 다 저작하면 발산을 직렬로 만들어 놓고 이름만 병렬로 바꾼 것이고, 저작하지 않고 비슷한 프롬프트를 N개 뿌리면 전부 같은 학습 분포 최빈값으로 회귀한다. 병렬성이 연산 층에서는 진짜고 정보 층에서는 가짜인 경우다.

**왜 lane 티어를 인터뷰어보다 낮추는가.** lane은 경계가 정해진 증거 조각에 대한 단일 관점 적대적 점검이라 여러 lane의 모순을 가려내는 종합과 같은 티어를 요구하지 않는다. 그런데 티어를 명시하지 않으면 lane이 세션 티어를 상속하므로, 상위 티어로 `/interview`를 돌리면 모든 lane이 조용히 같은 티어로 돌아간다. 반대로 종합 전용 상위 티어 에이전트를 따로 두지는 않는다 — 최종 판정은 메인 인터뷰어가 갖고 있고, 메인 스레드는 사용자에게 물을 수 있는 유일한 표면이라 별도 종합 에이전트는 물을 수도 없이 메인으로 되돌아오는 중복 홉이다.

**왜 단일 `SKILL.md`인가.** 증거 모델, 질문 계약, 종료 루브릭, 저장 규칙은 어느 분기에서도 빠지면 안 된다. 항상 함께 읽어야 하는 내용을 reference로 나누면 토큰을 아끼지 못한 채 누락 가능한 라우팅 결정만 추가한다.

**왜 추가 hook·agent·workflow·script가 없는가.** 강제해야 할 반복 이벤트, 고정 오케스트레이션, 재사용 가능한 계산 인터페이스가 없다. 위험 검토의 형태는 프로젝트마다 달라 실행 시 동적으로 구성하고, 결정과 종합은 메인 인터뷰어가 유지한다.

- **2026-08-16 — extend (스킬 생성 및 검증)** — 승인된 B4~B14를 영문 단일 `.claude/skills/interview/SKILL.md`로 생성했다. 생성 직후와 `validated` 상태 갱신 후의 정적 검사 및 의미 검사가 모두 통과했으며, 실제 질문 품질을 평가하는 대화형 사용은 후속 실사용 검증으로 남겼다.
- **2026-08-16 — extend (질문 비용 원칙 반영 및 검증)** — 사용자가 계획 단계의 질문 부담보다 잘못 추측해 구현한 뒤 수정하는 부담이 훨씬 크다는 비대칭을 제시했다. 불필요한 질문은 계속 제거하되 방향 변경 질문을 체감 마찰만으로 생략하지 않는 B26을 스킬에 반영하고 정적·의미 검사를 통과해 `validated`로 갱신했다.
- **2026-08-22 — sync (외부 상속 행 정리)** — B1~B3을 `retired`로 옮겼다. **파일 복원이 아니다.** 이 세 행은 2026-08-16 명세 복구가 다른 저장소(Ouroboros)의 명세를 출발점으로 삼으면서 딸려 들어온 것이고, `CLAUDE.md`와 `.claude/settings.json`은 이 저장소에 존재한 적이 없다. 같은 이유로 두 구성 요소의 Component specs 절과 Ouroboros를 전제한 문서 제목·Context 문단도 함께 정리했다.
- **2026-08-22 — improve (발산 보강: 메커니즘이 아니라 인터페이스로)** — 실사용에서 인터뷰가 한 트랙만 파고드는 증상이 관찰됐다. 진단은 직렬 스레드의 자기 감사가 빈틈을 만든 프레임을 그대로 쓴다는 것이고, 처방은 스윕 명부를 대화로 내보내 프레임이 다른 관찰자인 사용자에게 판정을 넘기는 것이다(B27, B28). 함께 영향 스윕을 검증 가능하게 만들고(B29), 오프닝 브리프 이전 금지 목록에 서브에이전트 실행을 명시했으며(B30), 검토 lane의 기본 모델 티어를 인터뷰어 종합보다 낮췄다(B11). 최초 가설이던 dynamic workflow fan-out은 재검토 끝에 다시 기각했고 그 근거를 Design rationale에 남겼다 — B24·B25는 `declined` 유지다.
